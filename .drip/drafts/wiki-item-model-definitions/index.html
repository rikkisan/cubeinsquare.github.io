Item Model Definitions in Minecraft 1.21.4: Using minecraft:select Instead of Overrides

The move to Minecraft 1.21.4 breaks more than old file paths. It breaks the old habit of treating one item model JSON as both the art file and the routing brain. Item Model Definitions separate those jobs, and once you accept that split, the new system starts making sense.

Open resource-pack generator

Why old overrides stop feeling solid

For years the usual pattern was simple: place a base model in models/item, attach an overrides array, and let predicates choose which alternative model should render. It was flexible enough to carry thousands of packs, but it also mixed two separate responsibilities inside one place. The file was both the object and the dispatcher.

That old pattern was convenient because it hid the complexity. You could think in one file, one list, one growing pile of branches. But as soon as the item ecosystem became richer, with component-based identity and more explicit rendering states, the old setup started feeling like a cramped storage room. Mojang's answer in 1.21.4 was not to make overrides slightly nicer. It was to pull the routing layer out and give it its own home.

What Item Model Definitions actually are

In 1.21.4, the game can read item model logic from assets/<namespace>/items/. That file no longer pretends to be just a raw model. It is a definition layer that describes how the game should choose between visual outcomes. The visual model still exists, but the selection logic is now a separate object instead of a side effect stuffed into overrides.

The old override pattern

Here is the kind of model most creators already know. It is familiar for a reason: it used to be the normal way to route a vanilla item into custom art.

{
  "parent": "item/generated",
  "textures": {
    "layer0": "minecraft:item/paper"
  },
  "overrides": [
    {
      "predicate": { "custom_model_data": 12 },
      "model": "cubeinsquare:item/paper/archive_pass"
    }
  ]
}

This does two things at once. It tells the game what the base paper looks like, and it tells the game how to branch into another model. For small projects that was fine. For bigger systems it encouraged one long file with growing special cases and very little semantic clarity.

The new definition pattern

Now compare that with an Item Model Definition that uses minecraft:select. The new file says, more openly: the job here is to choose a rendering branch based on a known property.

{
  "model": {
    "type": "minecraft:select",
    "property": "minecraft:custom_model_data",
    "index": 0,
    "cases": [
      {
        "when": "archive_pass",
        "model": {
          "type": "minecraft:model",
          "model": "cubeinsquare:item/paper/archive_pass"
        }
      }
    ],
    "fallback": {
      "type": "minecraft:model",
      "model": "minecraft:item/paper"
    }
  }
}

Line-by-line explanation of the new file

"model": this is the root model definition object. It is not a raw art file. It is the top-level routing rule.

"type": "minecraft:select": this dispatcher chooses from discrete cases. Use it when an item should jump between named states such as archive_pass, vault_receipt, or ritual_key.

"property": "minecraft:custom_model_data": the branch source is the component itself, not the old predicate syntax.

"index": 0: the definition is reading from a specific slot in the structured payload. That matters because modern custom_model_data can hold more than one flavor of value.

"cases": this is the list of explicit branches. Each one says what should happen when a particular state is present.

"when": "archive_pass": this is where the system gets friendlier to humans. A readable string tells you far more than an old integer like 12 ever could.

"type": "minecraft:model": this branch resolves to a normal raw model file. In other words, the final art asset still exists in the model layer you already understand.

"fallback": if nothing matches, the item still needs a stable base render. That fallback keeps test items and incomplete commands from becoming missing-model chaos.

Why minecraft:select feels better for symbolic states

The biggest strength of minecraft:select is that it matches the way many server creators already think. A permit is a permit. A ritual contract is a ritual contract. A guild seal is a guild seal. These are discrete identities, not gradual measurements. That means a select-style dispatcher is often a cleaner fit than a number-heavy override list.

On an RP server, that clarity matters twice. First, it helps the pack author remember what each branch is for. Second, it helps future maintenance when somebody else has to trace a broken item. “The archive_pass branch is wrong” is much kinder than “somewhere around CustomModelData 12 something weird is happening.”

Where raw models still belong

Item Model Definitions do not replace the craft of building models. They replace the place where you describe when a model should be shown. The raw geometry or generated model still lives in the model layer. The change is that the logic no longer has to masquerade as just another item model file.

That split is healthy because it gives you two clearer responsibilities:

  • The definition decides which branch should render.
  • The raw model decides what that branch actually looks like.

When to use minecraft:select and when not to

Use minecraft:select when the item moves between clearly named states: pass versus receipt, charged relic versus dormant relic, one faction seal versus another. Use it when the state is symbolic.

Do not force everything into select if the item changes along a measurable scale. If the appearance depends on durability, charge, or another numeric progression, that is usually the territory of minecraft:range_dispatch. The difference is simple: select is for named branches, range dispatch is for measured ranges.

A useful mental split: symbolic versus continuous

SituationBetter fitReason
Guild pass, city permit, ritual sealminecraft:selectThe item is switching between named identities.
Battery charge, staff power, weapon wearminecraft:range_dispatchThe item is moving along a scale, not flipping between symbolic roles.
Boolean on/off appearanceminecraft:condition or select-like branchingThe state is simple and explicit.

Typical migration mistakes

  1. Treating the new file as a renamed override list. It is better to think of it as a routing definition with explicit dispatcher types.
  2. Keeping unreadable number habits where strings would help. If the state is symbolic, a readable label is usually easier to maintain.
  3. Forgetting the fallback. Without a fallback, testing becomes harder and broken branches become less obvious.
  4. Mixing routing logic and server identity carelessly. Rendering state and hidden logic can relate to each other, but they are not automatically the same concern.
  5. Only converting the pack and not the commands. The visual routing and the item payload changed together. A half-migrated workflow still hurts.

What this means for a real workflow

If you are building with the pack generator, the custom item builder, villager trades, and your own RP systems, the ideal flow becomes much cleaner than before:

  1. Decide the item's symbolic identity in a readable way.
  2. Build the raw model and texture as art assets.
  3. Use an Item Model Definition to route the identity to the correct model.
  4. Keep hidden validation in custom_data or another explicit server-facing place.
  5. Test the command and the render together.

That is the real gift of the new system. It forces each layer to say what job it is doing.

Practical conclusion

Item Model Definitions are not just Mojang moving files around for fun. They are a structural answer to an old mess. The old override model let one file act as both art and routing. The new system separates those concerns and gives you named dispatcher types that better match the real shape of item logic.

If your item changes between symbolic states, minecraft:select is usually the right place to start. Once you make that mental shift, the rest of 1.21.4 begins to feel less like random breakage and more like a more legible rendering architecture.

FAQ

Do raw item model files still exist in 1.21.4?

Yes. The important change is that routing logic moves into Item Model Definitions under the items layer. Raw models still exist and still matter.

Is minecraft:select a direct one-to-one replacement for overrides?

Not exactly. It solves a similar routing problem, but it lives in a more explicit architecture and works better when you think in named states instead of a pile of old predicate branches.

Should I always switch from numbers to strings?

Not always. Numeric logic still makes sense for measured values. But if the item is really a named thing, like a pass or relic, readable symbolic states are often a better fit.

When should I use range_dispatch instead?

Use it when the item appearance should react to a continuous range such as charge, damage, or some other numeric progression rather than a discrete named identity.

What usually breaks first during migration?

Usually not the PNG itself. The first real failures tend to be command payloads, branch routing, and the assumptions old admin documentation still makes about where render logic lives.
